    Backup and upgrade

    Back up and restore the SQLite file and the secret key. Upgrade by replacing the program.

    What to back up

    You need to back up 2 things:

    1. The database, hsp.db in the data folder.
    2. The secret key, hsp.key in the data folder (or HSP_SECRET_KEY in your env file, if you set the key yourself).
    Keep the key

    If you lose the key, the stored member passwords are unrecoverable and the server does not start on that database. The server never makes a new key when hsp.db exists. Back up the data folder: it holds both hsp.db and hsp.key. Keep a copy in a safe place, not on the server computer.

    Back up the database

    Use the backup command of SQLite. It makes a complete, correct copy while the server is running. The sqlite3 tool is not part of HotspotPlus Lite, so install it if you do not have it.

    sqlite3 hsp.db ".backup backup-$(date +%F).db"

    Run it in the data folder, or give the full path of hsp.db. On Windows, use sqlite3.exe and choose the backup file name yourself. Do not copy hsp.db alone while the server runs: recent changes can still be in hsp.db-wal. To run the backup every night on Linux, add a line like this with crontab -e. In cron, each percent sign needs a backslash before it:

    0 3 * * * sqlite3 /var/lib/hotspotpluslight/hsp.db ".backup /backups/hsp-$(date +\%F).db"

    There is no backup or restore feature inside the program.

    Restore

    1. Stop the server.
    2. Put the backup file in the data folder as hsp.db, and delete any old hsp.db-wal and hsp.db-shm files there.
    3. Start the server with the data folder that holds both hsp.db and hsp.key. If you use an env file with HSP_SECRET_KEY, use the same key.

    To move the server to a new computer, copy the database (from a backup) and the key to it. Then start the program there.

    Upgrade

    To upgrade, you replace the program and restart it. The database migrations (changes to the database layout) run by themselves at start and only go forward. Make a backup first. You cannot go back to an older program on a migrated database, but you can restore the backup.

    Linux (systemd)

    curl -LO https://github.com/pysf/HotspotPlusLight/releases/latest/download/hotspotpluslight-linux-amd64.tar.gz
tar -xzf hotspotpluslight-linux-amd64.tar.gz
sudo systemctl stop hotspotpluslight
sudo install -o hotspotpluslight -g hotspotpluslight -m 755 hotspotpluslight /var/lib/hotspotpluslight/hotspotpluslight
sudo systemctl start hotspotpluslight

    This is the path that service install uses. Use your own folder if you chose one with --dir.

    Windows service

    .\hotspotpluslight.exe service stop
# replace hotspotpluslight.exe with the new file, in the same place
.\hotspotpluslight.exe service start

    macOS or a plain run

    Stop the program with Ctrl+C or SIGTERM. Replace the file and start it again.

    The server can tell you when a newer version exists. Once a day it asks GitHub for the latest release, and the admin panel shows Version X is available with a link to the Updates page. The page has the release notes and a Check now button. You can turn this off with the Check for updates setting.

    Update from the admin page

    When a newer version exists and the program can update itself, the Updates page has an Update now button. Press it and confirm. The server downloads the new version from the GitHub release, checks its SHA-256 hash, makes a copy of the database (hsp.db.bak-<old version> in the data folder), and replaces the program file. The old program stays next to it as hotspotpluslight.old. The page shows each step. The admin panel is down for a moment when the program restarts; online members stay connected. If the hash does not match, nothing is changed.

    The button is hidden, with a reason, when the program file is not writable, the release has no file for your system, or the program is a development build. Then update by hand as shown above.

    Restart and automatic rollback

    After the files are swapped the program restarts itself. Under a Windows service or systemd it exits and the service manager starts the new file (exit code 75; systemd needs Restart=always or Restart=on-failure). If you started the program by hand, it starts the new file itself. The Updates page reloads when the new version answers. macOS is manual only.

    The new version has 60 seconds to answer on its own /healthz. If it does not start, or it is not healthy in time (it started twice without becoming healthy, or 60 seconds pass), the old program file and the database copy are put back and the old version starts again. The admin panel then shows The last update to vX failed and was rolled back until you dismiss it. Changes made after the update started are lost, because the database copy is from just before the update. The failed files are kept as hotspotpluslight.bad and hsp.db.failed-<version> in case you want to look at them. A deliberate restart of the program during the first 60 seconds does not count as a failed start, and a healthy new version is never rolled back later. Before the swap the new file is run once with version; if that fails nothing is changed. If the rollback itself cannot be done, the panel says so and the program starts as it is.

    On a Windows service, a database copy that takes more than about 30 seconds can hit the service start timeout (error 1053). Only very large databases are affected.

    Check the version with hotspotpluslight version. When the database was upgraded, the log shows migrations applied with a count. The version is stored inside the program, not in the file name, so the download links never change.

    What is kept

    Finished sessions older than 90 days are removed. You change this with the Keep finished sessions (days) setting on the Settings page; 0 keeps them forever. The daily usage history and the members are kept.
