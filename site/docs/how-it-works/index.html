    How it works

    The login checks, the reply attributes, accounting, the two layers of limits and how Disconnect works.

    The login checks

    When a member logs in, the router sends an Access-Request with the user name and the password (PAP). The server checks these in order and stops at the first one that fails. The failure becomes a reject with that code (see Reason codes).

    #CheckCode when it fails
    1The member exists (ignoring case) and the password is right.INVALID_CREDENTIALS
    2The member is active.INACTIVE_USER
    3The member has a plan, and the plan still exists.NO_PLAN, PLAN_REMOVED
    4The member's expiry time has not passed.EXPIRED
    5Today is inside the validity period. If it is not and the plan renews automatically, the period is renewed and the checks go on.NO_ACTIVE_SUBSCRIPTION
    6Data is left (plan data plus extra data, minus the usage). Unlimited plans pass.OUT_OF_BULK
    7Time is left. Unlimited plans pass.OUT_OF_TIME
    8The member has fewer open sessions than the plan allows.NO_MORE_SESSION

    A CHAP or MS-CHAP login is rejected with UNSUPPORTED_AUTH_METHOD. The validity period starts when the member is created or renewed, not at the first login. A session counts as open until the router ends it, or until it has not sent an update for the accounting interval plus 60 seconds.

    What the router gets

    If every check passes, the server sends an Access-Accept with these attributes:

    AttributeValue
    Session-TimeoutThe smallest of: the time left in the plan, the time until the member's expiry, and the time until the end of the validity period. At least 1 second. Always sent.
    Acct-Interim-IntervalThe accounting interval from Settings (60 seconds by default).
    Mikrotik-Rate-LimitThe plan speed, the same for download and upload, with a burst of four times the speed for 8 seconds (no burst is sent when the burst would be above 12,000,000 kbps). Only when the plan has a speed limit.
    Mikrotik-Recv-Limit, Mikrotik-Xmit-LimitThe bytes left, the same value in both. Only when the plan has a data limit.
    Mikrotik-Recv-Limit-Gigawords, Mikrotik-Xmit-Limit-GigawordsThe high part of the bytes left, for more than 4 GiB. Only when it is above 0.
    Check on your router

    How RouterOS reads each attribute is on the hardware check list of the project and is not confirmed yet. Test a small plan on your router before you rely on it.

    Accounting

    The router sends Start, Interim (every accounting interval) and Stop packets with the totals of the session. The server turns the totals into usage:

    • Download is Acct-Output-Octets and upload is Acct-Input-Octets, each with its Gigawords part. Time is Acct-Session-Time.
    • The totals are per session, so the server adds only the change since the last packet. A packet that arrives twice adds nothing.
    • Usage is kept per validity period and goes back to zero when the period is renewed. The daily history for the Usage page is kept.
    • If a member has no MAC address yet, the address from the first accounting packet is stored.
    • The server always answers the router at once. The limit checks below happen after the answer.

    The time of a packet is the time the server received it.

    Two layers of limits

    1. Layer 1: the router. It gets Session-Timeout, the data limits and the rate limit at login, and ends the session or limits the speed by itself.
    2. Layer 2: the server. After each Start or Interim of an open session, the server checks the member again with the login rules. If the member must not be online (for example the data is used up, the plan was made smaller, the expiry time has passed, or the validity period of a plan without auto-renew has ended), it sends a Disconnect request. The session then ends with the cause Server: CODE.

    So a change you make in the admin panel acts at the member's next Interim update, at most one accounting interval later. Disabling or deleting a member disconnects the sessions at once. If a Disconnect fails, the server tries again later, and gives up after 3 failed tries with a warning in the log.

    Disconnect (kick)

    The Kick button on the Online now page, and the automatic kicks above, send a RADIUS Disconnect-Request to the router on the Disconnect port (3799 by default), with the user name and the session details. If the router answers ACK, the session is marked ended with the cause Admin-Reset (or Server: CODE). If the router refuses or does not answer, the admin sees an error and the session stays in the list. The router must accept incoming RADIUS on that port, see Router setup.

    After login

    After a successful login the router opens alogin.html, which sends the member to the status page. The status page is on the router and shows what the router knows. It does not ask the server.

    For diagrams of these flows, see the README on GitHub.
