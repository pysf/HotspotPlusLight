    Architecture and decisions

    The parts of HotspotPlus Lite, why it is one program with one SQLite file, and the key design decisions.

    The parts

    PartWhat it does
    RADIUS serverAnswers login requests on UDP 1812 and accounting on UDP 1813, and sends Disconnect requests to the router. Built on layeh.com/radius.
    Admin panelPages built on the server (chi router, templ components, htmx), with our own CSS and small JavaScript modules. No build step.
    Business rulesPlain Go functions with no input or output and no clock reads: the login decision, quota, units and password rules. Each rule has one implementation, used by both RADIUS and the admin panel.
    ServicesMembers, plans, sessions, vouchers and admin login. They depend on small interfaces, so tests use hand-written fakes.
    StoreSQLite through modernc.org/sqlite (no cgo). Parameterized SQL only, and forward-only migrations.
    Router pagesThe 8 hotspot folders and the RouterOS script are built into the program and zipped on request.

    Only one package, internal/app, connects all the parts. The README has the package map and the diagrams: README on GitHub.

    One HTTP listener

    The server has one HTTP listener (the admin panel on :8080, with /healthz) and 2 UDP listeners for RADIUS. There is no public web server and no API for the login page. The router hosts the login page by itself. The admin panel uses plain HTTP, and it must not be reachable from the hotspot network.

    One SQLite file

    All data is in hsp.db in the data folder, in WAL mode. The server opens it as 2 pools: 1 write connection and 8 read connections. With a single write connection, writers wait their turn in Go and never fight over the lock. Every write is a short transaction. Accounting packets are handled one at a time and saved before the router gets its answer. While the server runs, the files hsp.db-wal and hsp.db-shm appear next to the database. See Backup and upgrade for how to copy it safely.

    Migrations are built into the program. They run when the server starts, one transaction each and forward only. The server checks their checksums.

    Key decisions

    DecisionReason
    One business, one admin, one router, MikroTik onlyIt keeps the program small. HotspotPlus serves many businesses from one install, and that is not needed here.
    PAP onlyThe login page sends the password to the router, and the router passes it on to the server. A CHAP login fails with a clear code, so a wrong router setting is easy to see.
    RADIUS built in, no FreeRADIUSOne program to run and nothing else to set up.
    SQLite onlyOne file to back up. No Redis, no Kafka, no database server.
    Member passwords stored encrypted (AES-GCM)The admin can look up a password and reprint a voucher. This is why you must back up the secret key (hsp.key).
    Plain HTTP on a local networkA choice for simplicity. Keep the admin panel off the hotspot network and off the internet.
    Login pages live on the routerMembers see the page before they have internet. The page needs nothing from the server.
    Two layers of limitsThe router limits are the first line, but RouterOS behavior can vary. The server's Disconnect requests close the gap.
    Expiry is enforcedThe server checks a member's expiry time at login and again while the member is online.
    First login is admin / admin, then a forced changeNo generated password is printed, so there is nothing to miss. The Password page has strong enough rules and a Generate button.
    A plan that members use cannot be deletedIt would leave members without a plan.
    Own CSS, no framework, no build stepThe admin panel needs no Node tools, and the CSS stays small and easy to read.

    The full list, with decision ids, is in PLAN.md.

    How it is tested

    End-to-end tests start the real program and use only real interfaces: UDP RADIUS from a fake router, HTTP and the command line. Domain rules and services also have unit tests. A capacity test with a simulated router raised the number of online members step by step. It passed 30,000 on one machine and failed at 40,000. See the performance section of the README.
